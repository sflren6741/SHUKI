# 🔧 運用見直し（ops-review スキル）

初回セットアップ後に使う、**運用をユーザーと対話しながら見直し・改善する**スキル。

`/setup` が「空欄を埋めるQ&A」、`/audit-tasks` が「タスクDBの棚卸し」なら、
このスキルは **「AI運用そのもの（エージェント・ルール・スケジュール・価値観）を、ユーザーと会話しながら今の現実に合わせて磨き直す」** 場。

> ⚠️ **これは “壊れ検出ツール” ではない。**
> 「整合が取れているか（壊れていないか）」はあくまで入口の一材料。
> 本題は **「この運用は今のユーザーにとって本当に機能しているか？もっと良くできないか？」を問い、対話で決めて直す** こと。
> だから ❌0件で終わっても「問題なし、解散」ではなく、「では今の運用で引っかかっている所はある？」と踏み込む。

---

## 起動方法

- `/ops-review` — 全体を対話的に見直す（きっかけを聞くところから）
- `/ops-review エージェント` — 8体の役割分担・使われ方を見直す
- `/ops-review ルール集` — AI運用ルール集の陳腐化・実態とのズレを見直す
- `/ops-review スケジュール` — Task Scheduler / Local AI の定期実行が今も意味を持つか見直す
- `/ops-review 価値観` — 価値観3軸の変更を全ファイルに波及
- `/ops-review areas` — Areas 定義の整合

引数があればその領域から入るが、**引数があっても対話はスキップしない**。

---

## 見直しの3レンズ

検出も提案も、必ず次の3つの視点で見る。どれか1つに偏らない。

| レンズ | 問い | 例 |
|---|---|---|
| 🔗 **整合（壊れ）** | 記述が実態とズレていないか | デッド参照・旧価値観ワード・体数の食い違い |
| 🌀 **摩擦（回ってない）** | 定義はあるが実際に機能しているか | 一度も発火していないスケジュール、使われないルール、形骸化した手順 |
| 🌱 **改善（もっと良く）** | 今のユーザーにとってより良い形があるか | 役割の重複・空白、ルールの過不足、対話に移すべき無人処理 |

整合は機械的に拾える。**摩擦と改善は対話でしか出てこない** — だからこのスキルの核は会話にある。

---

## Phase 1: きっかけと範囲を聞く

引数の有無に関わらず、まず一言聞いて温度感を合わせる：

> 「今日はどこから見直したいですか？ 何かきっかけ（エージェント追加した／ルールが実態と合ってない気がする／しばらく経った／特定の引っかかり）があれば教えてください。なければ全体をざっと一緒に見ます。」

ユーザーの答えで、3レンズのどれを厚く見るか・どの領域から入るかを決める。

---

## Phase 2: 現状把握（材料を集める。まだ直さない）

対話の素材を集めるフェーズ。整合スキャンに加えて、**実態の観察**もする。

### 整合スキャン（🔗 レンズ）

- **A 価値観3軸**: `🪪 Identity.md` と `哲学・価値観.md` の3軸を読み、`.claude/agents/*.md` と `00_Intranet/AI運用ルール集（イントラ）/` を Grep で旧ワード照合
- **B エージェント参照**: `.claude/agents/` を Glob して実在名を確定 → `00_Intranet/README.md` / `🏢 AI組織図 ＆ RACI.md` / `📋 エージェント共通テンプレート.md` のデッド参照・記載漏れを検出
- **C ルール集の陳腐化**: `00_Intranet/AI運用ルール集（イントラ）/` 各ファイルを Read。体制・モデルID・パス・最終更新日（90日以上空いていないか）を確認
- **D Areas**: `🪪 Identity.md` の Area 一覧と `05_Areas/*.md` の実在・`AGENTS.md` §📐 の area 11値が一致するか

### 実態の観察（🌀 レンズ）

整合だけでなく「本当に回っているか」を見るために、可能な範囲で：

- `<data>/system/agent-runs/` / `<data>/system/monitoring/` — 各エージェント・スケジュールが直近で実際に発火しているか（定義はあるが沈黙しているものは摩擦候補）
- **`07_Logs/レポート/運用/エージェント稼働サマリー.md` の「提案」欄を必ず読む** — infra は Read専用・検出のみなので、提案は着手されないまま毎週再掲され溜まる。**infra＝検出（無人）／ops-review＝判断＋実行の出口（有人）** という役割分担。未着手の提案を 🌀/🌱 として対話に持ち込む
- `⚙️ 定期便カタログ.md` の便と、実際の出力先（`07_Logs/朝スタンドアップ/` 等）に最近の生成物があるか
- ルールに書かれた手順が、最近のタスク・ログで実際に踏まれているか

> ⚠️ 履歴ファイル（`agent-runs/` `monitoring/` 等）は**読むだけ**。編集しない。

材料が揃ったら Phase 3 へ。**この時点では何も直さない。**

---

## Phase 3: 対話による見直し（このスキルの核）

集めた材料を「指摘リスト」ではなく **「一緒に考える問い」** に変えて出す。
判定を下すのではなく、ユーザーの意図・実感を引き出して、直す形を**一緒に**決める。

### 出し方

```
## 今回見えたこと

### 🔗 整合のズレ（事実として直せるもの）
1. [ファイル:行] ◯◯が△△を指している — 実態は□□。直す？

### 🌀 引っかかり（回ってない／形骸化してそう）
1. [対象] ◯◯は定義はあるが直近◯週間発火していない。まだ要る？ 残す/やめる/変える？

### 🌱 改善の余地（もっと良くできそう）
1. [対象] 今は◯◯だが、△△にした方が今のユーザーの動き方に合うかも。どう思う？

まずどれから話しますか？
```

### 対話の作法

- **整合（🔗）** は事実なので「直す/直さない」を確認すれば足りる
- **摩擦・改善（🌀🌱）** はユーザーの意図が正解 → **問いを投げ、答えを待つ**。AIが結論を断定しない
- 1件ずつ深掘りしてよい。「これはなぜこうなってる？」と背景を聞き、運用の理由を言語化してから直す
- ユーザーが「それは意図的」と言ったものは**改善対象から外す**（例: 「人の情熱には情熱で応える」は本人の原則であり3軸ではない＝意図的）
- 押し付けない。提案は「こうしたら？」まで。決めるのはユーザー

---

## Phase 4: 合意した変更を適用

ユーザーが「これは直す／こう変える」と決めたものだけ、1件ずつ反映する。

1. 対象を Read して現在の内容を確認
2. **変更前/変更後**を明示：
   ```
   変更前: `ユーザーの3軸（情熱・誠実・調和）`
   変更後: `ユーザーの3軸（成長・誠実・調和）`
   ファイル: reviewer.md L78
   ```
3. OK を得て Edit
4. **波及**: 同じ事実が複数ファイルにある場合（体数・Area名・エージェント名など）、波及先を列挙して「まとめて揃える？」と確認 — 1か所だけ直して他がズレる事態を防ぐ
5. 役割・制約そのものを変える改善（例: エージェントの担当範囲を変える）は、`.claude/agents/<name>.md` が唯一の正なので**そこを編集**し、組織図・README は追従させる

---

## Phase 5: 記録

変更を入れたら、最後に履歴を残す：

- `00_Intranet/AI運用ルール集（イントラ）/🏁 変更ログ＆運用ルール.md` に1行追記（日付・何を・なぜ）
- ユーザーの職業・役割・Area・価値観・禁止ゾーンに関わる変更が出た場合は、AGENTS.md §📜 ルール9 に従い **確認を取ってから** Identity / 哲学・価値観 / Areas を更新
- `<data>/system/skill-runs.jsonl` に1行 append する（このスキルは生成物を残さないため、これが唯一の実行記録＝SHUKIダッシュボードのスキル推奨バッジ用。書式: `{"ts":"YYYY-MM-DD HH:MM","skill":"ops-review","source":"skill"}`）

完了サマリー：

```
## ✅ ops-review 完了

### 直した（X件）
- [ファイル]: 変更の1行サマリー（🔗整合 / 🌀摩擦 / 🌱改善 の別）

### 話した上で「今のままでいい」と決めたもの（X件）
- [対象]: 残す理由（ユーザーの意図）

### 持ち越し・次回
- [対象]: 理由
```

---

## 🚫 やってはいけないこと

- ❌ 対話を飛ばして一括修正に走る（整合のズレですら「直す？」と一言確認する。摩擦・改善は必ず会話）
- ❌ 確認なくファイルを書き換える（必ず変更前/後を見せてから）
- ❌ 「壊れてないので問題なし」で終える（❌0件でも摩擦・改善を必ず問う）
- ❌ AIが運用の良し悪しを断定する（提案まで。決めるのはユーザー）
- ❌ 代筆禁止ゾーン宛文章・大きな判断をAIが書く（代筆禁止ゾーン継承）
- ❌ スキャン範囲外（vault本体ノート・タスクDB）を勝手に修正する
- ❌ 履歴ファイル（agent-runs / monitoring / 変更ログの過去分）を改変する

---

## 🔄 セルフQAの3行

```
- 事実チェック: 検出・観察は実ファイルを読んで確認したか。摩擦の指摘を実態（発火履歴等）の裏取りなしに断定していないか
- トーン: 判定の押し付けでなく、ユーザーの意図を引き出す問いになっているか。決定をユーザーに委ねているか
- アンチスロップ: 「全体的に問題なし」で済ませず、整合だけでなく摩擦・改善まで具体に踏み込んだか
```
