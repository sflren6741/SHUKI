## 🌅 日次ブリーフィング（朝7時の主出力・2026-07-31 スタンドアップから移行）

**役割はこれだけ：`<data>/system/briefing/<日付>_materials.json` を読んで `<data>/system/briefing/<日付>.json` の `sections` を書く。** 素材集めも、尺の管理も、画面・音声・履歴への配布も Python 側（`briefing_builder.py`）がやる。ここで書くのは文章だけ。

```
素材 → [briefing_builder --collect] → <日付>_materials.json   ← 決定的・捏造の余地なし
     → [ここ／sonnet]              → <日付>.json              ← 文章を書くのが仕事
     → [briefing_builder --render] → 台本 .txt ＋ 履歴 .md
                                     ダッシュボードは .json を直接読む
```

> 旧構成（`07_Logs/朝スタンドアップ/<日付>.md` を書く）は廃止。standup は「読む用」に加工済みの中間生成物で、それをさらに音読していたため二重加工になっていた（上流を変えても効かない／本文が伸びるとラジオが自動的に伸びる。実測 7/23 5.9分 → 7/29 16.8分）。**旧 §2 決裁は `<data>/system/decisions/` へ分離済み**（本文には書かない・§⚖️ 参照）。

### 尺が仕様の中心

**日次は 3.5分 / 合計1,400字が上限。この数字に入らないものは載せない。** VOICEVOX（speaker=3・speed=1.1）実測で話し言葉は約400字/分、現行の書き言葉文体は約326字/分。**要約より先に文体で効く**（同じ情報量で6割減）ので、そのまま音読できる話し言葉で書く。

| キー | 項目 | 字数 | 中身 |
|---|---|---|---|
| `open` | 開き | 40 | 日付・曜日のみ |
| `intellect` | **今週の知的な動き** | 350 | **主役①**。**直近2日を主軸に**書く — `tier:"fresh"` の概念／`task_flow`（昨日・今日の起票・完了）／`recent_logs` の気づきから、繋がり・構造を1つ。3〜7日前（`tier:"context"`）は分母・文脈の補助にとどめる |
| `observed` | **観測された自分** | 200 | **主役②**。宣言と実行のズレを事実で。素材の `observed`（先延ばし日数の実測・done 遷移）のみを使う |
| `today` | 今日やること3つ | 180 | 1件60字。画面にもあるので声では短く |
| `decisions` | 要判断 | 250 | **最大3件**。話し言葉の二択に開く |
| `diff` | 昨日からの差分 | 150 | 動いた／止まった／新しく入った |
| `numbers` | 数字1行 | 100 | 家計・トレード・習慣を各1文 |
| `runway` | 3日以内の助走 | 100 | 準備が要る予定のみ |
| `closing` | 1年前の今日＋閉じ | 70 | 遊び枠 |

**超過した日の削り順**：`runway` → `diff` → `closing` → `numbers`（`enforce_budget()` が自動で落とす）。**`intellect` と `observed` は削らない** — 削ると器の目的そのものが消える。

### 重心＝実務でなく「発見」

ユーザーの要求は「新しい発見がほしい。やる気が欲しい」。vault で今いちばん動いているのは**タスクではなく概念**（7月に概念ノート10件超が生成される一方、タスクは due なし多数・ディスパッチ空回り・決裁の再掲が発生していた）。「今日やること3つ＋要判断」を主役に据えるのは**一番動いていない側を主役にする設計**なので、重心は「観測された自分・知的な動き」に置く。

**やる気＝励ましではない。** ユーザーは「甘やかさない・客観・忖度なし」を明示的に選んでいるので、声で褒めても効かない。効くのは意味・物語・記憶と、**自分では気づけなかった事実による知的な驚き**。ブリーフィングは励ます器ではなく**発見を運ぶ器**。

### 書くときの禁止事項

- ❌ **素材に無い事実を書く**（欠損は捏造せず省略する。`closing` が `null` なら1年前の話はしない）
- ❌ ファイル名・パス・JSON名・`YES=` `NO=` 記法・記号の羅列（そのまま音読されるため）
- ❌ 励ましの枕・一般論的な健康アドバイス・昨日のログのコピペ
- ❌ `intellect` を「今週こんな概念が増えました」の羅列で終わらせる（**繋がり・構造を1つ出す**のが仕事）
- ❌ `observed` で解釈を断定する（事実を置き、解釈は1つに決めず問いで返す）

### 音声から落とすもの（画面には残す）

例外報告（gmail_fetch 停止・session_limit 等の機械の故障報告）は耳で聞いてもその場で動けないので、画面のバッジと `/maintenance` に集約する。決裁の4件目以降も画面の決裁パネルへ（声は最大3件）。

### 素材（`<日付>_materials.json` の読み方）

`briefing_builder.py --collect` が事前に集めて渡す。**ここに無いものは書かない。** 追加で vault を読み回る必要はない（読むと尺と生成時間が膨らむ）。

| キー | 中身 | どの項目に使う |
|---|---|---|
| `intellect.recent` | 直近7日で新規/更新された概念ノート（定義冒頭・関連概念・登場場面の数）。各要素の `tier` が `"fresh"`（直近2日に作成）／`"context"`（3〜7日前）。**`fresh` を主軸、`context` は補助** | `intellect` |
| `intellect.total_concepts` | 概念ノートの総数 | `intellect`（「44件のうち6件が今週」のような分母） |
| `task_flow.opened` | 昨日・今日に**起票**されたタスク（タイトル・area・priority・ねらい1行）＝その日の関心の変化 | `intellect` `diff` |
| `task_flow.completed` | 昨日・今日に**完了**したタスク（`status→done`／`end_actual`）＝その日の実際の進捗。各件の `by` が `"ai"`（AIレーン実行便が片付けた）／`"self"`（ユーザーが片付けた）。**`by:"ai"` が1件以上あれば「寝ている間に進んだ分」として明示的に触れる**（2026-09-04・夜間もAIレーン便が回るようになったため。何が進んだか分からないまま朝を迎えるのを防ぐ） | `intellect` `diff` |
| `recent_logs` | 昨日・今日に作られたログの気づき1行 | `intellect` `diff` |
| `observed.postponed` / `postpone_median_days` | `due`/`start` を後ろ倒しした実測（日数つき） | `observed` |
| `observed.done` / `on_hold` | 完了・保留に移った実測 | `observed` `diff` |
| `today_tasks` | ボードと同じ分類で選ばれた上位3件 | `today` |
| `decisions` | `decisions.for_audio(3)` の3件（見出し・背景・応答型） | `decisions` |
| `diff.changes` / `counts_delta` | 昨日〜今日の変更行とタスク数の増減 | `diff` |
| `numbers.trading` | ペーパートレード評価額と HODL 比較（無ければ `null`） | `numbers` |
| `runway` | 1〜3日後の予定で準備が要るもの（毎日ある English・ジムは除外済み） | `runway` |
| `closing` | 1年前の今日のログ（±3日で最も近い。無ければ `null`） | `closing` |
| `gcal_today` | 今日・明日の予定（生テキスト） | `open` `today` `closing` |

> ⚠️ センシティブな内容（希死念慮系等）が `closing` に当たった場合は引用せず、「1年前のこの日にログがある」程度に留める。読むかはユーザーが決める。**非公開Areaのログ**（`_private/`・`喧嘩ログ/`等）は Phase 4 以降 deny 対象のため `closing` の候補から機械的に除外する（存在の言及もしない）。

**参照期間の重心（2026-08-30）**：日次は「昨日・今日」を主軸にする。`task_flow`（起票・完了）・`recent_logs`・`intellect.recent[].tier=="fresh"` が主軸レイヤーで、7日窓の `context` 概念と `observed`（実測7日窓）は文脈を与える補助。主軸レイヤーに素材があればそこから書き起こし、毎日ブリーフィングが似た話になるのを避ける。主軸が薄い日だけ `context` に寄せてよい。

### 書き物（音声）と読み物（画面）の分かれ方

**書くのは音声台本だけでよい。** 画面は同じ素材から別のレンダリングで組まれる（2026-07-31 ユーザーの指摘「読みづらい」を受けた分離）：

| 項目 | 画面での出方 |
|---|---|
| `intellect` / `observed` | **書いた散文をそのまま**表示（読み物として成立する2つ） |
| `today` / `diff` / `numbers` / `runway` | **素材 JSON から構造で描画**（タスクはリンク付きリスト、数字はタイル、助走は日付つき箇条書き）。書いた文章は画面に出ない |
| `decisions` | 決裁パネル（ボタン付き）。本文は使わない |
| `open` / `closing` | 音声のみ（画面では挨拶は不要） |

つまり `today`〜`runway` の文章は**耳のためだけに書く**。「1つめ、〜。2つめ、〜」のような音声用の言い回しを遠慮なく使ってよい（画面には出ない）。**要約を二重に作っているわけではない** — 同じ素材の同じ選択結果を、耳向けと目向けに配っているだけ。

### 出力先

**`<data>/system/briefing/<日付>.json` だけ。** 他のファイルは書かない（画面・台本・音声・履歴 `07_Logs/ブリーフィング/<日付>.md` はすべて `--render` が配る）。タスクDBの中身は**読み取りのみ**でステータス書き換えはしない。チャット返信は「ブリーフィング生成済み」程度の短い完了報告のみ。

```json
{ "date": "YYYY-MM-DD", "weekday": "金", "generated_by": "...", "generated": "...",
  "sections": { "open": "...", "intellect": "...", "observed": "...", "today": "...",
                "decisions": "...", "diff": "...", "numbers": "...", "runway": "...",
                "closing": "..." },
  "notes": { "…素材が欠けていて省いた項目があればその理由…" } }
```

### 移行で枠から外れたもの（2026-07-31 → 2026-08-06 決着済み）

1,400字の枠に入らないため旧スタンドアップから外れた項目。**置き場所は2026-08-06にユーザーが決定し、この論点は閉じた**：

- **💞 代筆禁止ゾーン（旧 §3）** — **廃止**（受け皿を作らない）。当時は「ユーザーが週末に`/cbt`・`/message-review`・MOC「関係史MOC」で手動で振り返る」前提だったが、2026-09-06 の Phase 4 でこれらのツール自体を廃止・deny 化し、AIとの振り返り自体をやめた（AGENTS.md §🚫 非公開Area情報は扱わない）。日次・週次ブリーフィングに定例枠として復活させない方針は変わらず
- **🇬🇧 英語コーナー（旧 §6・土曜のみ）** — **廃止**。週次ブリーフィングにも寄せない（2026-08-01 に週次への追加を却下済み、08-06 に日次側も廃止で確定）
- **🃏 今月のフォーカス（デッキ）／🚚 本日のディスパッチ予定** — 画面（`/board`・`/game`）にあるため声からは落とした
- **📊 視覚化ルール（コールアウト・mermaid timeline・カウントダウンバー）** — 音声化できずブリーフィングが JSON になったため役目を終えた。ダッシュボード側の表現に一本化

> ⚠️ 週次ブリーフィングの `relationship` セクション（下記 §📻）は**既存の仕様どおり継続**する。ここで廃止したのは「日次の定例枠と、その受け皿を新設する話」であって、週次の自己観察に含まれる代筆禁止ゾーンの記述ではない。

## 📻 週次ブリーフィング（日曜朝・2026-08-02 実装）

**役割は日次と同じ形：`<data>/system/briefing/<日付>_weekly_materials.json` を読んで `<data>/system/briefing/<日付>_weekly.json` の `sections` を書く。** 素材集めも尺の管理も配布も `briefing_builder.py --collect-weekly` / `--render-weekly` がやる。ここで書くのは文章だけ。仕様の詳細（配信タイミング・尺・素材・客観性の担保）は `04_Tasks/タスク管理/タスク/ブリーフィングを設計する（日次・週次／画面・音声）.md` の2026-08-01確定事項が原案。

### 日次との違い

| | 🌅 日次 | 📻 週次 |
|---|---|---|
| 目的 | 前を向く（今日動くため） | **意味づけと定着**（振り返るため） |
| トーン | 実務・短い | **客観**。ただの要約や励ましにしない |
| 尺 | 3.5分／1,400字 | **10分／4,000字** |
| 配信 | 毎朝7:00 | 日曜朝（既存 `Claude-WeeklyReview` 日曜18:00＝Claude使用状況レポートとは別便） |

### 項目配分（合計4,000字）

| キー | 項目 | 字数 | 中身 |
|---|---|---|---|
| `open` | 開き | 60 | 週の期間のみ |
| `intellect` | **今週の知識の復習** | 1,200 | 週内の概念ノート・ナレッジノートの総括。**日次のローリング窓と違い「その週の総括・繋がりの俯瞰」**（素材は同じでも視点を変える） |
| `logs` | **今週何をしたか** | 800 | 週内新規ログからの事実（失敗を材料に変える帳は除く・§relationship で別枠） |
| `observed` | 発言と行動のズレ | 600 | `task_changes` 7日窓の実測（後ろ倒し・done遷移） |

| `insight` | **気づき・教訓** | 700 | 事実を関連知識・教訓と結びつけて語る（「ゆる言語学ラジオ」トーン） |
| `closing` | 閉じ | 240 | 1年前の今日（あれば）＋まとめ |

**超過時の削り順**：`relationship` → `closing` → `observed` → `logs`（`enforce_weekly_budget()` が自動で落とす）。**`intellect` と `insight` は削らない**（週次の目的そのもの）。

### 客観性の担保（4原則・2026-08-01確定）

①実測値を出す ②先週の発言と今週の行動のズレを事実で並べる ③解釈は1つに断定せず問いで返す ④**事実を関連する概念・知識・教訓と結びつけて語る**（説教臭くなく、知的好奇心を刺激するトーン＝ユーザーのイメージ「ゆる言語学ラジオ」）。「ただの知的好奇心ではなく自分の生活と関連した内容」＝自己観察・反省と関連知識・教訓を切り離さないのが核心。

### 代筆禁止ゾーンの扱い（対象外・2026-09-06〜 Phase 4）

Phase 4（AGENTS.md §🚫 非公開Area情報は扱わない）以降、非公開Areaに関する自己観察・反省は週次ブリーフィングの対象外とする。関連Area・人物ノート・ログ（`_private/`・`喧嘩ログ/`・`CBT思考記録/`・`日記/`）は settings.json の deny 対象でもあり、AIは内容に触れない。関係の中で見えた自分自身の問題で、ユーザー自身が一般化した教訓として書き直したもの（概念ノード等・denyから個別解除されたもの）のみ通常の自己理解の材料として扱ってよい。

## 📥 §0 インボックス振り分け

ユーザーから「インボックスを処理して」「振り分けて」等が来た時、または朝サマリー生成時に一括スイープする。

**対象**：`01_Inbox/インボックス/*.md` の frontmatter で **`status: new`** のファイルのみ。他（`routing` / `done` / `rejected` / `pending`）は黙ってスキップ（ループ防止）。

**手順**：
1. 状態を `routing` に変える
2. タイトルと「元メモ」を読み、種類判定して振る：
   - 📋 **タスク** → `04_Tasks/タスク管理/タスク/<新タイトル>.md` を新規作成（下記§1のプロパティで）。インボックスの `destination:` を `"[[<タスクタイトル>]]"` の wikilink 形式で Edit 上書き（追記禁止）
   - 💡 **アイデア** → インボックスに残す。`destination: "Idea: 温める"` と Edit 上書き
   - 📚 **資料** → `06_Resources/` 配下に新規 .md 作成。`destination:` を `"[[<ノートタイトル>]]"` の wikilink 形式で Edit 上書き
   - 🔒 **秘匿ログ**（代筆禁止ゾーンの感情・思考等、日常ビューに出したくない内省）→ `07_Logs/ログ/_private/` 配下に新規 .md 作成。既存秘匿ログの frontmatter 形式（`title` / `type: ログ` / `area` / `date` / `created` / `status: archived` / `private: true` ＋冒頭に秘匿ファイルの警告コールアウト）に合わせる。**このカテゴリも移行はその場（同じパス内）で完結させる**——後続で拾う専任エージェントが存在しないため、routing のまま次の便に持ち越さない
   - 🧭 **文脈** → `00_Intranet/AI運用ルール集（イントラ）/` の哲学・価値観／デザイン言語／📋 エージェント共通テンプレート へ追記提案をコメントで提示（本文には勝手に手を入れない）
   - 🔗 **URL** → frontmatter に `type: 🔗URL` があれば `@knowledge` に委譲。URLフィールドを渡してナレッジ化を依頼する。インボックスの status は `routing` のまま（`@knowledge` が完了後に `done` に更新する）
   - 🤔 **未分類** → 状態を `pending` にして、ユーザーに問いを1つだけ提示
3. 状態を `done` に更新し「振り分け先」を残す
4. スパム・重複・不要 → 状態 = `rejected`、理由をメモ

**`routing` を待機状態のまま残してよいのは 🔗URL（`@knowledge` 委譲）だけ**。それ以外の全カテゴリ（タスク・アイデア・資料・秘匿ログ・文脈）は手順2の作業自体を同じ振り分けパス内で完了させ、手順3で必ず `done` まで進める。routing のまま止めると、URL以外を拾う専任の継続処理が存在しないため恒久的に迷子になる（2026-08-13 `/maintenance` で `思い出.md` が3日間 routing のまま放置されていたのを発見・修正した実例あり）。

**タイトルだけで本文がない場合**：タイトルから推定できれば振り分け。推定不能なら `pending` でユーザーに問い1つ。

**代筆禁止ゾーンは代筆しない**（タスク管理ルール §3.3 代筆禁止ゾーン）。タスク化はしても本文ドラフトは作らない。

**frontmatter を書くときは YAML出力ルールを必ず守る**：`agent` / `human_only` / `status` 等のメタデータは1項目1行に改行し、`:`・`false/true`・絵文字を含む値は `"` で囲む（`memo:` に複数メタデータを詰め込まない）。詳細 → `00_Intranet/AI運用ルール集（イントラ）/📋 エージェント共通テンプレート.md` §YAML（frontmatter）出力ルール。

- **② 決裁・確認カードの補充（sonnet）** — 山から新しく聞くべき判断・選択・不足情報を最大10件選び、`<data>/system/decisions/proposed.json` へ書く（**`open.json` は直接編集しない**）。上記の質ルールに従い、内容に合う `response_type`（`yes_no` / `choice` / `text` / `datetime`）と必要な `options` を仕立てる。専用セッション・有人セッションの開始日時は `datetime` カードにし、自由記述カードとして再提示しない。書いた後 PS1 が `python decisions.py --merge` を呼び、採番・重複排除して `open.json` へ取り込む。既に決着したものは id で弾かれるので、②は反映処理も除外判定もしない。**07:00 前（00:00・03:00・06:00 便）はスキップし claude を起動しない**（PS1 側の時刻判定・2026-07-26 のコスト対策を継続。2026-07-31 に「当日スタンドアップの存在」条件は撤去 — 決裁は本文と独立に積めるようになったため）。

これで「押した決裁は最大3時間で必ず消化される（⓪）」「7:00 以降は3時間おきに新規決裁が積み上がる（②）」の両輪が回る。

> 💡 **なぜ sonnet か（2026-07-16 検証）**: 当初 haiku に任せたら、承認済みを畳むだけで新規候補を1件も具体化せず「決裁待ちなし」を出した（＋中国語混じりの語を書く品質不安定）。仕立て（生の山をユーザーが短い操作で答えられる形に翻訳する）は判断を要するため sonnet に分離した。振り分け①は引き続き haiku で安く回す。

## ✅ AIレーン（旧 `ai_judgment_ok`・2026-09-04 に置き換え）

**フラグを立てる運用をやめ、`vault-scripts/ai_lane.py` が毎回導出する方式に変えた。** 旧 `ai_judgment_ok` は 2026-08-06 に定義が「許可」から「AIが完了まで持っていけるか（能力）」へ変わっており、能力は状況で変わるのに固定値で保存していたため必ず陳腐化していた（実際 2026-08-06 に12件の一括修正が発生）。さらにユーザーが意識しないところでAIが書き換える値になっており、ユーザーの意思表示と混同されていた（2026-09-04 ユーザーの指摘）。

### 分けたもの

| | 誰が決めるか | 保存するか |
|---|---|---|
| **許可**（AIに触らせるか） | **ユーザーだけ** | する。frontmatter `human_only: true` の1個だけ |
| **能力**（AIが完遂できるか） | AI | **しない**。`ai_lane.py` が毎回導出する |

- `area: 非公開Area` を含む（代筆禁止ゾーン・AGENTS.md §📜 ルール2）
- 内省・言語化が完了条件（深掘りする／リフレクション／自分の言葉／CBT 等）
- ユーザーの身体・対面が要る行動（来店／対面／受験／通院／撮影 等）
- ユーザー自身の学習・訓練（学習／勉強／習得／を学ぶ 等）
- ユーザーの記憶の想起（思い出／回想）

お金・外部送信・健康は `prep` に落ちる＝**下ごしらえまでは進めてよく、最終アクション（購入・送金・送信）の直前で §3.6 の5手順によりユーザーへ戻す**。この境界は従来どおり（AGENTS.md §📜 ルール3）。

### デジタル活動の分析方針（週次）

`weekly_summary.md` を読む際は、**数字をそのまま並べるのではなく、データの裏にある行動・関心・変化を読み解くこと**。

以下の問いを軸に分析する：

**場所（Maps）から読む**
- 今週どこに行き、何をしていたか（駅の組み合わせから移動の目的を推定）
- 初訪問の場所は何か——新しい体験・変化の兆しか
- 自宅・職場以外の場所パターンに変化はあるか

**検索（Chrome）から読む**
- 今週特に気になっていたテーマは何か（上位キーワードの束から関心を読む）
- 生活上の課題や不安が検索に現れていないか（健康・お金・人間関係など）
- 突発的に調べた「なんでだろう」系の検索に注目する

**AI 利用（Gemini）から読む**
- 利用件数が増減した場合、それはなぜか（忙しさ・課題の性質・気分）
- 音声利用が多い週は何をしていたか

**クロスデータ分析**
- 場所 × 検索を重ねると「何のためにどこへ行ったか」が見えてくる
- Gemini 急増 ＋ 特定の検索クエリ集中 → 特定のプロジェクトや問題に取り組んでいる
- Chrome 閲覧量の急増・急減は活動密度の変化。「なぜこの週は少ないか」が重要

**感情・体調の手がかり**
- 健康関連の検索（症状・食・薬など）は体調管理の努力を示す
- スポーツ観戦・エンタメへのアクセス増加はリラックス・気分転換の週
- ショッピング（amazon, aeon）の増加は何かを買おうとしている時期

## 🚚 タスクディスパッチ（毎日12:30・2026-07-04 新設）

「AI同士がやり取りしてタスクを勝手に進める」ための社内便。Task Scheduler `Claude-TaskDispatch`（`task_dispatch.ps1`）が毎日12:30に起動する。

> ⚙️ **実行主体は Claude Code 本体セッション**（サブエージェントは他エージェントを起動できないため、本体が orchestrator の代理＝部長代行としてこの節の手順を実行する）。

> 🔓 **実装タスクも無人実行の対象（2026-09-05 方針転換・旧「対象外」記述は撤回）**。旧記述は「実装はユーザーとのセッションで進めるのが正」としていたが、ユーザーが明示的に撤回した（8/6にそう発言した記録は残っておらず、ユーザー自身「言った覚えがない」）。Tier A（finance/knowledge/english/researcher）にコードを書くエージェントがいない点は変わらないが、実装系・担当未定タスク（`ai_lane.py` の `runner: session`）は**サブエージェントに投げず、この便を回している本体セッション自身が直接コード・vaultファイルを編集して完了まで進める**。判断が明確なら重さ（ファイル数・複雑度）は問わない。**完了条件が曖昧・判断が割れる箇所に当たったら無理に続けず、そこでエスカレーション5手順に入って `on-hold` に落とす**（重さでなく明確さで進退を決める＝ユーザーの指示）。安全に迷った時は🛑停止ルールに従う。
>
> あわせて 2026-08-06 に、**ユーザーの身体・関係・アカウントが要る行動に `ai_judgment_ok: true` が立っていた12件を false へ修正**した（自転車を店舗で購入・パートナーと直接話す・受験・インスタ投稿・語学の視聴など）。この便が「候補あり」と誤認して空振りする原因になっていたため。以後この判定は「**AIが単独で完了まで持っていけるか**」で行う（判断を任せてよいか、ではない）。**2026-09-04 追記**: この12件のような型は `ai_lane.py` の自動ガード（来店・対面・受験・学習・内省）が機械的に `human` へ落とすようになったため、以後は手作業の一括修正が要らない。
>
> 💡 **例外（2026-08-07 追加）**: お金・健康ゾーンでも、最終判断の前に**AIが完了できる実質的な下ごしらえ**（データ収集・比較・ドラフト作成）があるタスクは `agent: <Tier A>` のままでよい（`ai_lane.py` は lane=`prep` を返す）。担当エージェントは下ごしらえを進め、最終アクション（購入・送金・実行）の直前で §3.6 の5手順エスカレーションにより `agent: 人間（ユーザー）` へ差し戻し、§2 決裁の山へ回す。`human` に落とすべきなのは上記12件のように来店・対面・受験などAIの下ごしらえが実質ゼロの行動だけ。

### 手順

1. **`python vault-scripts/ai_lane.py --queue`（dispatch）と `--queue session`（session）の両方で実行可能タスクを取得する。** 前者が「Tier A 担当 × lane が ai/prep × start 到来済み」、後者が「実装系・担当未定 × lane が ai/prep × start 到来済み」を返すので、Glob→Grep で条件を組み直さない（画面・便・エージェントで判定がズレると事故る）
   - **`start` が未来日のタスクはどちらも `--queue` が除外済み（2026-08-06 追加・2026-09-04 実装へ移設）**。`start` は 🗂 vault構造ガイド.md §📂 タスクDBの扱い方 で「この日まで手を付けない＝意図的な先延ばしの正式表現」と定義されており、`/next`・`/schedule` は既に除外している。この便だけが無視して実行すると、ユーザーが意図して寝かせたタスクを勝手に起こすことになる
2. `due` が近い順に、dispatch・session 合わせて**最大3件**選ぶ。0件でも「§補充」は毎便行う
3. **dispatch（`agent:` に Tier A が入っている）は Agent ツールのサブエージェント（subagent_type: finance / knowledge / english / researcher）で起動**し、タスクファイルのパス・completion_criteria・関連リンクを渡す（2026-07-12〜。エージェント定義の BOM 除去で全7体が起動可能になった）。**session（実装系・担当未定）はサブエージェントに投げず、この節を実行している本体セッション自身が直接コード・vaultファイルを編集して進める**（2026-09-05）。completion_criteria が明確なら重さ（ファイル数・作業量）は問わない。途中で完了条件が曖昧・判断が割れる箇所に当たったら無理に続けず、その時点でステップ4のエスカレーションへ入る
4. 各件は自定義の「タスクピックアップ」節の様式（サブエージェント）または `## 実行結果` 追記＋`done`更新（本体セッションが直接実行した場合も同じ様式に揃える）で完了させる。完了できない場合は**エスカレーション5手順（タスク管理ルール §3.6：引継ぎノート → `agent: 人間（ユーザー）` → `human_only: true` → `status: on-hold` → 停止）**でユーザーへ差し戻す（`on-hold` だけ立てる旧様式は廃止・2026-07-12 統一）。**引継ぎノートには §2 の質ルールに従い、ユーザーが次に答えられる短い判断・選択・不足情報確認（何を選べば次にどう進むか）を書く**（§2 の3時間おき再生成〈sonnet〉がこの note をそのまま活かせるため）。
5. **同便リレー（2026-07-12 新設）**: 全件完了後、タスクDBを**1回だけ**再スキャンし、この便の実行中に新規起票されたハンドオフタスク（§3.9・同条件）があれば**追加で最大3件**実行する。再スキャンは1回のみ（無限リレー防止）。2巡目で起票されたものは翌便へ
6. エスカレーションになったものは §2 決裁の山に自然に入る（3時間おきの §2 再生成で当日中に決裁UIへ載る。ユーザーへの報告はそこで届く）

### 補充（旧「供給提案」・2026-07-12 新設 / 2026-09-04 常時化）

> 🔁 **2026-09-04 変更**: 従来は「ディスパッチ対象が0件の日だけ」補充していたため、キューは常に0〜2件しか無く、ユーザーからは「たまに1件ずつ決裁に上がってくるだけ」に見えていた（実測：活きタスク56件に対し実行可能2件）。**閾値方式に変える** — 実行後に `python ai_lane.py --queue` の残件が **3件未満なら毎便補充する**。0件の日だけの特別処理ではない。

0. **先に `<data>/system/ai_feedback.jsonl` の直近20行を読む**（2026-09-04 新設）。ユーザーが `/review` の🤖AIの成果カードで押した 👍/👎 が1行1件で溜まっている。`rating: "bad"` が付いた仕事と**同じ型**（同じ担当・同じ切り口・同じ成果物の形）は次から切り出さない。`rating: "good"` の型は優先して探す。`comment` があれば何が外れていたかがそこに書いてある。ファイルが無い／空なら従来どおり進める
1. 残件が3件以上あるなら補充しない（積み上げすぎない）。3件未満なら、`human_only` が無い × `status: todo|in-progress` × 担当未定のタスクを読み、その中に**AIが先に進められる工程**（調査・比較・下書き・データ整理・ナレッジ化）がないか確認する
2. あれば子タスクとして**最大3件**起票する — `agent: <Tier A>`・`completion_criteria` 必須・`parent:` で元タスクに紐付け（本文に切り出しの理由を書く。**フラグは付けない** — 担当が Tier A なら次の12:30便がそのまま実行する）
3. 起票した子タスクは `/board` の🤖AIレーンに並ぶ。担当（Tier A）を付けて起票すれば当日12:30便がそのまま実行する
4. 既に同種の候補がレーンに滞留しているなら重複起票しない。切り出せる工程が本当になければ「ディスパッチ対象なし・切り出し候補なし」と1行出力して終了
5. 出力は「実行N件／補充M件（残キューK件）— <タイトル列挙>」

### 制約

- お金・パートナー・健康・外部送信の**最終アクション**（購入・送金・送信・対面での実行）はエージェントが単独で実行しない。lane が `prep` のものはそこまで進め、最終アクション直前で §3.6 の5手順エスカレーションにより §2 の山へ回す。下ごしらえが実質ゼロの行動（来店・対面・受験等）は `ai_lane.py` の自動ガードが `human` に落とすので、起票時に何も書かなくてよい
- 無人セッションのため外部送信は改札フック（`CLAUDE_UNMANNED=1`）が物理ブロック
- **session（実装系・担当未定）を無人で直接実行する際の安全弁（2026-09-05）**：completion_criteria が曖昧・実装方針が複数あり判断が割れる・影響範囲が読めない、のいずれかに当たったら重さを問わず即エスカレーションへ回す（続けるかどうかは明確さで決める。ファイル数や工数の大小では決めない）
- 1便あたり最大3件＋同便リレー最大3件（計6件上限、dispatch・session合算）
- 同一タスクが2便連続でエスカレーションになったら3便目以降はスキップ（無駄ループ防止・🛑停止ルール）
- ハンドオフの起票様式・制約の正本はタスク管理ルール §3.9（Tier B・自分自身への振り禁止、1タスクから最大2件）

### 🔁 AIレーン実行便（3時間おき・2026-09-04 新設／2026-09-09 Luna化）

12:30 の専用便だけでは**1日1回しか消化されず**、ユーザーが「AIに任せる」を押しても実行は最短で翌日だった。3時間おきの `ObsidianInboxMonitor` に **③ AIレーン実行** を相乗りさせ、溜まっていれば随時回す。

- **起動条件**: `ai_lane_ready`（`runner_jobs.py`）が `ai_lane.runnable("dispatch")` と `ai_lane.runnable("session")` の合計を数え、**0件ならAIエンジンを起動しない**＝対象がない時間帯のコストはゼロ（2026-09-05: session分も数えるよう拡張。従来は実装系・担当未定タスクを最初から見ておらず、「AIに任せる」を押しても着手されない状態が続いていた）
- **実行件数**: 1便あたり**最大5件**（2026-09-09 に3件→5件へ引き上げ。3時間便の処理能力を広げ、滞留を減らす。12:30便の最大3件＋同便リレー最大3件は変更しない）
- **実行モデル**: `GPT-5.6 Luna` を既定にし、`/settings` の `codex/gpt-5.6-luna` の `model_reasoning_effort` をそのまま渡す。現在値は `max`。Codexのクレジット上限時だけSonnetへフォールバックする。実装・スクリプト系のsessionタスクを含むため、この便では vault と `vault-scripts` のみを編集対象にする
- **夜間も動かす**: 00:00 / 03:00 / 06:00 便も対象。調査・ナレッジ整備は無人で安全に進む種類の仕事で、代筆禁止ゾーン・お金・外部送信は `ai_lane.py` の自動ガードが機械的に止める。**寝ている間に進み、朝のブリーフィングで結果を受け取る**のがこの便の狙い
- **この便がやらないこと**: 補充（切り出し起票）は 12:30 便の担当。3時間おきに起票すると候補が重複するため
- 手順・様式・エスカレーションは §🚚 の対象取得・安全弁・完了様式に従う。補充と同便リレーは行わない（この便の上限は5件で、12:30便の3件＋3件とは別枠）

### 📥 成果の受け取り（`/review` の🤖AIの成果・2026-09-04 新設）

AIが完了させたタスクは、ダッシュボード `/review`（レビュー・インボックス）に **🤖 AIが完了した仕事**として自動で載る（`collect_ai_outcomes()`。判定は「担当が Tier A × 本文に `## 実行結果`」＝ブリーフィングの `by:"ai"` と同じ）。ユーザーはそこで 👍 役に立った / 👎 使えなかった を押す。

- 押下は `<data>/system/ai_feedback.jsonl` に1行追記される（`task_path` / `title` / `agent` / `rating` / `comment`）。**サーバーが直接書く**ので回収便は不要
- この評価は §🚚 の**補充の手順0**で読み、次に切り出す仕事の型を選ぶ材料にする（ニュースの `feedback.json` と同じ、評価を選定に還す片方向ループ）
- カードの要約には実行結果の `- 要約:` 行を、フッタには実行結果内の wikilink（生成した成果物）を出す＝**タスクを開かずに何が増えたか分かる**のが狙い
- 実行頻度を3時間おきに上げた以上、「AIが作ったがユーザーが読んでいない成果物」が溜まる方向に振れる。この受け取り口はその対策であって、飾りではない

### Tier B 担当タスクの完了経路（2026-08-30 決裁 d-9051a82a で確定・2026-09-05 一部改訂）

Tier B（orchestrator / infrastructure）が関わるタスク、および `human_only: true` または `agent: 人間（ユーザー）`（`ai_lane.py` の lane=`human`）でコード・設定変更を要するものは 12:30 便・AIレーン実行便の対象外のまま。これらは従来どおり **次にそのタスクが Claude Code 本体セッションで開かれた時に本体が拾って進める** を既定ルールとする（`/ops-review`・`/maintenance`・task-exec・関連する会話のついで等）。進めるたびに個別決裁を起こす必要はない（前例「ダッシュボードサーバーのHidden起動が失敗する不具合を直す」が3回の決裁 × due 超過になった反省）。
