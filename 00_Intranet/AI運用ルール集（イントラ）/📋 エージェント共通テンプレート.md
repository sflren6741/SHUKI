## エスカレーション・ハンドオフ手順

判断の境界線を超えた、または完了条件を満たせないと判断した瞬間に止まる。これは「失敗」ではなく**正しい完了形**（「完了できなかった」ではなく「判断材料を揃えてユーザーに渡した」がゴール）。

**ユーザーへの差し戻し（エスカレーション）の正本は [[✅ タスク管理ルール]] §3.6**（引継ぎノート記録 → `agent` を `人間（ユーザー）` に → `human_only: true` を立てる → `status` を `on-hold` に → 停止してユーザー判断待ち。2026-07-12 に status 変更を手順へ統合）。

**エージェント間ハンドオフの正本は同 §3.9**（自分の領分外の後続工程はハンドオフタスクを起票 → 12:30 ディスパッチ便の同便リレーまたは翌便が自動実行。Tier B・自分自身への振り禁止・1タスクから最大2件）。

エージェント間・人間↔AIで仕事を引き継ぐときの原則（会話は消える。**書いたものだけが残る**）：

- **推測で補わない** — 不確定事項は「未解決」として明記する
- **タスク本文に貼る** — チャットに頼らず `04_Tasks/タスク管理/タスク/` のファイル本文に記録
- **一タスク一ドラフト** — 複数タスクを1チャットに混ぜない
- **参照コンテキストをメンションする** — wikilink か相対パスで（URLはデッドリンクになりやすい）

## 作成前ルール（計画先出し・既存流用）（2026-07-03 導入）

新しい成果物（レポート様式・スクリプト・Project 構造・複数ファイルにまたがる変更）を、いきなり完成品から作り始めない。目的は「的外れな方向への全力疾走」を防ぎ、時間とトークンを節約すること。

1. **既存資産を先に探す** — 同種のテンプレ・過去の類似成果物・既存スクリプトを Glob/Grep で探し、あれば流用・拡張する。ゼロから作るのは見つからなかった時だけ
2. **まず計画・構成案を出す** — 対象が大きい場合（目安: 新規ファイル3件以上、または vault に新しい様式・構造を持ち込む場合）は、着手前に「何を・どこへ・どう作るか」の短い計画を提示してユーザーの確認を取る

定型の単発出力（インボックス振り分け・既存テンプレ準拠のログ・スタンドアップ等）はこの限りではない。

## AIの態度（同意で流さない）（2026-07-03 導入）

- **曖昧・情報不足なら推測で進めず質問する**（[[🛑 停止ルール（ストップ条件）]] §S.3 と同じ）
- **指示や前提がおかしい・より良い方法があると思ったら、着手前に反対意見・代替案を1回述べる**。ユーザーが「それでも進めて」と言ったら従う
- 同意・賞賛で会話を埋めない。壁打ち相手としての価値は率直さにある（セルフQAは事後チェック、これは着手前の異議申し立て。両者は補完関係）

## 記録ルール（再利用可能な情報は残す）（2026-07-03 導入）

会話・作業の中で出た**再利用可能な情報は、言われなくてもできる限りメモとして残す**。チャット本文にしか存在しない状態（セッションが終わると消える）を作らない。

| 情報の種類 | 書き先 |
|---|---|
| 重要な決定とその理由 | 該当 Project hub / タスクのコメント / [[🏁 変更ログ＆運用ルール]] |
| ボツ案と却下理由 | 同上（採用案の隣に1〜2行。「作らないと決めた記録」も価値がある） |
| アイデア・後で考えること | `01_Inbox/インボックス/`（`status: new` で投入 → orchestrator が拾う） |
| 失敗の教訓 | [[📚 教訓集]]（🛑 停止ルール §S.4） |
| 繰り返し登場するテーマ・原則 | 概念ノード（`06_Resources/Resources/概念/`・既存ルール） |
| **運用インフラ・常駐サービス・コネクタ・外部接続の新設/変更**（例: ダッシュボード・通知チャネル・Tailscale等の遠隔・音声・新スクリプト基盤） | **[[🛠 Technical Setup]]**（人間が「今どこに何が繋がっているか」を辿る正）。**スケジュールタスク**は `⚙️ 定期便カタログ.md`。AI向け背景メモを別に残す場合も vault の正は Technical Setup と明記する（2026-07-16 追加。ダッシュボードがClaudeメモリだけに落ちて人間向けイントラに浮上しなかった漏れを受けて） |

- 迷ったらインボックスへ（振り分けは通常フローに乗る）
- 代筆禁止ゾーン・外部送信ルールは従来どおり継承する（記録のためでも代筆禁止ゾーン宛文章は作らない）

## 異なる視点（斜め上フィードバック）（2026-07-30 導入）

「客観的な視点」ではなく「異なる視点」。中立に事実を並べることではなく、能動的に情報の扱い方を変えて、本人がまだ気づいていない構造を見せることを指す（2026-07-30 の対話で定義確定）。

**定義**：頼まれた内容をそのまま生成するだけに留まらず、以下いずれかの軸で情報の扱い方をズラす。

| 軸 | 内容 | 具体例 |
|---|---|---|
| 器（メディア） | 同じ中身でも表現形式を変える | テキストの計画→1枚のビジュアル（資格ロードマップの図解が好例） |
| 階層（メタ視点） | 頼まれた同一階層でなく、一段上の構造に触れる | 「計画を立てて」→計画そのものでなく「どう見せるか」を提案する |
| 並置（再配置） | 既存の要素を足さずに並べ替える | 別々のインボックスやログの共通構造・矛盾を横断的に指摘する |

**軸B（知識の深さ）**：論文・実証研究に基づく新しい知識も面白さの一因だが、器・階層・並置とは別軸で扱う。**適用場面を分ける**：
- 器・階層・並置（軽量）→ 日常の示唆パート（レポート結論・振り返りの気づき欄）で頻繁に使ってよい
- 知識の深さ（重量）→ `/research`・概念ノードの深掘り・動画制作など、もともと重い成果物を作る場面に限定する。毎日のブリーフィングに論文を持ち込むのはコスト対効果が悪い

**適用ルール**：
- **データを羅列する場所では使わない**（示唆・気づきを渡す場所限定）
- **頻度を義務化しない**。「毎回1つ斜め上コメントを入れる」という固定枠にした瞬間、それ自体が予測可能なフォーマットに堕ちて自己矛盾する（判断力の問題であって、チェックリック項目ではない）
- 客観的な中立記述と混同しない。異なる視点は「能動的に構造を変える」行為であり、両論併記や事実の中立列挙とは別物

## 実行ログ（.log 一本化・2026-07-02）

**エージェントは実行ログファイル（.md run log）を作成しない。** 記録は次の2層で自動的に残る：

- **スケジュール起動**: PS1 ラッパーが `99_System/agent-runs/<系統>_YYYY-MM-DD.log`（1日1ファイル追記）に全出力を自動記録する。形式は `=== Start: HH:mm:ss ===` → 出力全文 → `=== Done: HH:mm:ss | result: success|error|session_limit ===`
- **手動起動**: チャット自体が記録。残すべき成果は vault 本体（ナレッジ・ログ・タスク・monitoring）へ書く

`session_limit` の検知は PS1 層が行い `.log` の `result:` に記録する（判定は「exit code 非0 かつ `resets <時刻>` 明示」に限定・2026-07-02 厳格化）。infrastructure の夜間集計（NightQA）が `.log` をパースし `99_System/monitoring/エージェント稼働サマリー.md` に集約する（独立の履歴ファイルは持たない・2026-07-05 一本化）。

> ⛔ **例外（ログ）**: エージェントの実行ログ・作業報告の本文には wikilink を作らない。`99_System/agent-runs/` のログや、チャットへの報告本文でファイル名・タスク名を書くときは `[[]]` を使わずプレーンテキストにする（ログの `[[]]` が実ノートのバックリンク／グラフをログ参照で汚すため）。frontmatter の構造プロパティ（`area:`/`parent:`/`children:`）は従来どおり wikilink 可。既存ログは遡って直さない。

## 📊 レポート可視化ガイドライン（2026-06-14 導入）

レポート（日次ブリーフィング・週次レビュー・月次家計・活動レポート等）を生成するエージェントは、**データが多い箇所を「文字だけ」で並べず、図・表・コールアウトで認知負荷を下げる**こと。目的は「人間がぱっと、ストレスなく理解できる」アウトプット。Obsidian は mermaid・コールアウトをネイティブレンダリングするため追加コスト不要。

### 使い分け（データの形 → 図の種類）

| データの形 | 推奨ビジュアル | 記法 |
|---|---|---|
| 時系列の推移（件数・金額・距離） | 折れ線/棒グラフ | mermaid `xychart-beta` |
| カテゴリ別の内訳・構成比 | 円グラフ | mermaid `pie` |
| 出来事の年表・1日の流れ | タイムライン | mermaid `timeline`（⚠️ ラベルに `:` 禁止＝`22時`） |
| 関係・ネットワーク・分岐 | 有向グラフ | mermaid `graph TD/LR` |
| 関心・テーマの広がり | マインドマップ | mermaid `mindmap` |
| 期間ごとのまとまり（曜日・週） | 表（ボックス） | Markdown table |
| 緊急度・重要度の強調 | コールアウト | `> [!danger]` / `> [!warning]` / `> [!info]` |
| 進捗・達成率 | バー | `▓▓▓▓░░` or `████░░` のテキストバー |

参考実装（フル活用例）: [[デジタル活動全期間分析（図版）]]（timeline / xychart / pie / mindmap / graph を網羅）。

### 4つの鉄則

1. **図は本文の補助。図だけで本文を置き換えない**（散文・箇条書きも残す）。
2. **数値は実データと一致させる。捏造しない**。グラフの値は本文の数字と必ず合わせる。
3. **該当データが無い図は黙って省く**（空の図・0だらけのグラフを出さない）。
4. **やりすぎない**。1レポートにつき図は要点に絞る（情報を増やすためでなく、減らして見やすくするのが目的）。

> mermaid が壊れやすい点: `timeline` は `期間 : イベント` をコロン区切りするため**時刻の `22:00` がエラー**になる（`22時` と書く）。`pie`/`xychart` のラベルや数値に余計な記号を入れない。レンダリング未対応の環境では表にフォールバックする。

## YAML（frontmatter）出力ルール

frontmatter を書くすべてのエージェントは、以下を**必ず守る**。破ると Obsidian / パーサが「mapping values are not allowed here」等で frontmatter 全体を壊す。

1. **独立したメタデータ（`agent` / `human_only` / `status` / `area` 等）は、必ず1項目1行に改行して出力する。** 複数のメタデータを `memo:` などの1つの値の中にまとめて埋め込まない。

   ```yaml
   # ❌ NG（1つの値に詰め込み、コロンが値の途中に出て壊れる）
   memo: タスク化した。agent: infrastructure、human_only: false

   # ✅ OK（個別行に分離）
   memo: "タスク化した。"
   agent: infrastructure
   human_only: "false"
   ```

2. **値の文字列内に `:`（コロン）・`false`/`true`・絵文字・`#`・`「」` 等が含まれる場合は、値全体を必ず `"` で囲む。**

   ```yaml
   # ❌ NG
   status: ✅振り分け済
   human_only: false
   memo: A案（type:アイデア）とB案を比較

   # ✅ OK
   status: "✅振り分け済"
   human_only: "false"
   memo: "A案（type:アイデア）とB案を比較"
   ```

   - `true`/`false` を**真偽値として**使いたい場合のみクォート無し（例: 機械処理する boolean フラグ）。文字列メモの一部としての `false` は必ずクォートする。

3. 複数行テキストは `|`（リテラルブロック）を使い、各行をインデントする。

3.5. **`title:` を必ず入れる（2026-07-03 導入・vault_lint 検査対象）。** 値はファイル名（拡張子・ハッシュ抜き）と同じで良い。`"` で囲む。Obsidian 以外への移行時にファイル名の制約（禁止文字・文字数）で失われたタイトルを復元するための可搬性レイヤー。

書き終えたら frontmatter を一度見直し、各メタデータが個別行になっているか・`:` や絵文字を含む値がクォートされているかを確認してから保存する。

4. **既存ファイルの frontmatter キーを更新するときは、必ず Edit で既存行を置換する（新行追記禁止）。** テンプレートに空のプレースホルダー（例: `destination:`）が存在する場合でも同様。追記すると重複キーになり frontmatter 全体が壊れる。

   ```yaml
   # ❌ NG（追記すると重複キー）
   destination:          <- 元からある空行
   ...
   destination: "値"    <- 新たに追加 → YAML破損

   # ✅ OK（Edit で既存行を置換）
   destination: "値"    <- 空行を Edit で上書き
   ```
