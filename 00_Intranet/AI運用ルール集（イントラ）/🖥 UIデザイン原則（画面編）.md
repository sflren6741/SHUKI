# 🖥 UIデザイン原則（画面編）

## 2026-09-21 — Digital Agency guide applied to the shared dashboard

The user's redesign request adopts the [Digital Agency dashboard guide](https://www.digital.go.jp/resources/dashboard-guidebook), especially sections 3.4 (reading order and layout), 4.4 (clear hierarchy and restrained decoration), and 5.5 (accessibility).

- The selected presentation is `light` + `standard`: neutral gray canvas, white surfaces, one blue accent. Other themes and expressive skins remain available.
- `dashboard_settings.THEMES` owns palette values. `dashboard_theme.STANDARD_EXTRA_CSS` owns standard-style spacing, typography, flat surfaces and removal of decorative glow. Existing 8–12px rounding remains.
- `dashboard_ui` owns the opaque shared header, navigation, visible keyboard focus and reduced-motion handling. This supersedes the older translucent-header requirement below.
- Primary actions precede supporting details. No new metrics or inferred data are introduced by the redesign.
- Verified: six template/fixture pages at 1440, 390 and 320px; navigation open/Escape; keyboard focus; 30 theme/style combinations. The light palette's text, accent and semantic colors exceed 4.5:1 on both canvas and card backgrounds. This is not a full accessibility audit of every live chart.


> [!note] 🖥
>
> **SHUKIサーバー（`dashboard_server.py`・127.0.0.1:8765）の画面UIを作る/直すときのルール。**
> [[デザイン言語]] は文書・発信の作法（コールアウト色・文体）。こちらは**画面**（配色・配置・アフォーダンス）専用に分離した（2026-07-28、`base` 移植プロジェクトの土台整備で新設）。

## 🎯 大原則：並べない

`01_Inbox` に残る過去のフィードバック（振り分け済み）：

> 「タスクのボックスを見ると、数多くのタスクが並んでいてやる気にならない。**これは見た目の問題**」

vault の Obsidian `base`（一覧・表）を単純にブラウザへ移植すると、Obsidian で見て萎える表がサーバーでも萎える表になるだけになる。**画面UIの仕事は「一覧を出す」ことではなく「答えを1つ先に出す」こと**。一覧は答えの下に隠しておき、開く操作をした人だけが見る。

## 1. 色 — 意味の予約と識別の分離

トークンには2種類ある。**混ぜない**。

| 種別 | 例 | 用途 | 使ってよい場所 |
|---|---|---|---|
| 意味トークン | `--danger` `--warn` `--ok` `--info` | 状態・緊急度 | 期限バッジ・エラー・成功トースト |
| 識別トークン | Area 10色（`--area-仕事` 等）、レアリティ4色 | カテゴリの見分け | **アイコンと小さなタグの文字色だけ**。面・帯・強調に使わない |

- Area配色（**2026-08-06 サイバー配色へ刷新**）は `非公開Area#F2589D`｜`人間関係#D96BE8`｜`自己理解#A87BF0`｜`仕事#6C8AF2`｜`英語#4FA6E8`｜`時間管理#35BEDC`｜`ハンドボール#3FD0C4`｜`健康#46D6A5`｜`娯楽#63DD82`｜`お金#9BE05C`。**`dashboard_theme.py` の `AREA_C` が唯一の正**（JS側に複製しない。`--area-<英字キー>` を `getComputedStyle` で読む）
  - 旧配色はテラコッタ／マスタード／オリーブ等のアース系で、既定テーマ cool-dark（スレート×インディゴ）と系統が噛み合わず浮いていた。新パレットは寒色〜電子色を色相順に10等分し、テーマの `--accent`(#7c8cf5)・`--teal`(#4fd1c5)・`--blue`(#5aa9e6) と同じ系統に揃えてある
  - **ライトテーマ用に暗色版 `AREA_C_LIGHT` を別に持つ**。ネオン系は白地だとコントラスト 1.5〜3.0 しか出ずアイコンが読めない（実測）。白地 #f5f6fa に対し 3.5 以上になるまで暗くした同色相を配信する
- レアリティ配色は `伝説#b45309`｜`英雄#ec4899`｜`精鋭#0284c7`｜`新生#059669`（`concept_tree.py` の `RARITY` が元）。**収集品レイヤー（`/game` `/achievements`）限定**、実務画面には持ち込まない
- **画面コードに生の hex を直接書かない**。必ずトークン経由（`var(--xxx)`）。パレットが3箇所に分裂した過去の再発防止策
- **アクセント（`--accent`）は画面全体で1色に絞る**。「見やすいけどモダンに見えない」の主因は、彩度の高い色を同時に何本も主役として使ってしまうこと。意味トークン（`--danger`/`--warn`/`--ok`/`--info`）は状態表現なので別枠として共存してよいが、装飾目的で2本目のアクセントを足さない
- **ニュートラル（`--bg`/`--card`/`--line`/`--muted`）は「完全な無彩色」か「アクセントと同系統のわずかな色相を残す」かを毎回どちらかに決め切る**。中途半端に色相が混ざったニュートラルが「配色が微妙」に見える主因（2026-08-03・配色刷新プロジェクトでユーザーと実物比較して確認）

検証：本文コントラスト比 4.5:1・大文字（18px以上）3:1 を全トークン組で満たすこと。チャート系の色は dataviz skill の `validate_palette.js` を通す（既存ルール継承）。識別トークン（Area10色）は**アイコン＝graphical object なので 3:1 以上**、かつ**相互のCIE76色差20以上**を実測してから採用する。

## 1.5 形 — 一辺だけ塗らない・中途半端に丸めない（2026-08-06 追加）

ユーザーのフィードバック：「上だけや左側だけカードに色がついているのがかっこよく見えない」「微妙に丸まってるところがダサい」「もう少しサイバーっぽい、全体のテーマと統一感のある配色を」。

- **カードの一辺だけを色で塗らない**（`border-top: 3px solid <Area色>` / `border-left: 3px solid` 等）。
  - **理由（ユーザーの言語化・2026-08-06）**: 角丸のカードで一辺だけ塗ると、その辺が接する**2つの角で色が中途半端なカーブを描いて途切れる**。線の太さと角丸半径が噛み合わず、塗った部分の端が不自然に細く尖る。これが「ダサい」の正体で、色そのものの問題ではない
  - つまり **「一辺だけ塗る」と「角を丸める」の組み合わせが悪手**。どちらか片方なら成立しうる（角が直角なら帯はきれいに止まる）。SHUKIは**丸みを残す方を選んだ**ので、帯（一辺塗り）の側を廃止する（2026-09-15 に角丸2pxを撤回したため表現を修正）
  - **色はアイコン（と小さなタグの文字色）が持つ**。カードの枠線は四辺とも `--line` で均一にし、必要なら hover で枠色をわずかに寄せる程度に留める
- ~~**角丸は 2px（ほぼ直角）に統一**~~ → **撤回（2026-09-15）**。2026-08-06 にこう決めたが、**1年近く実装が一度も追従しなかった**（実測：`border-radius` 宣言のうち 2px は34件のみ、8px 38／12px 21／20px 19／6px 16／10px 16 …と非準拠が140箇所）。にもかかわらず誰も困っておらず、ユーザーが2026-09-15に実機で2px版と現行版を見比べて**「丸い方が良い」と判断**した。**原則の側を実態に合わせて改訂する**（守られないルールを残す方が害が大きい）
  - 現行の実態＝**8px / 12px を中心とした丸み**。これを既定とする。新規実装は周囲のカードに合わせる（孤立した値を足さない）ことだけ守る
  - 例外として**意図的に別の形を名乗る要素**は従来どおり：ピル（`999px`）・円形ドット（`50%`）・下からせり上がるドロワー（上辺のみ `16px`）
  - 角ばった見た目が欲しい時は、設定の**スタイル「角ばった」（`sharp` スキン）**を選ぶ。全要素を2pxに揃え、上記の例外だけ戻す（`dashboard_theme.SHARP_EXTRA_CSS`）。既定にはしない
  - ⚠️ **禁止は「一辺だけ塗る × 角丸」の組み合わせの方**であり、丸み自体ではない（上記の理由の通り、角で色が中途半端に途切れるのが問題）。この禁止は撤回しない
- 面（背景）に識別色を敷かない。敷くと画面全体が色づき、本来目を惹くべき状態色（期限・警告）が埋もれる

適用済み：`/board` の Areaカード・チップ、`/progress` の現在地バンド、`/habit` の候補カード。

## 2. 配置と階層 — 1画面1目的・逓減開示

- 1画面の最上位に置く「答え」は**1つだけ**（現行 `pick_top_action()` の🎯金色glowが実装例）
- 一覧・詳細はデフォルト折りたたみ。開くのは明示操作の後（`<details>` やモーダルで隠す）
- `01_Inbox` の過去フィードバック（振り分け済み）：「**人間がやらなければならないことがどこか1ページにまとまっていてほしい**」— UI再設計時の受け入れ基準

## 2.4 ツールバー — 同じ役割の操作は1つに畳み、役割はアイコンで示す（2026-08-08 追加）

`/board` のツールバーに、Areaのセレクト・ステータスのチェックボックス群・締切のセレクトという **同じ「絞り込み」なのに別々のUI**が横並びになり、さらに見た目が同じセレクトで並べ替え・グルーピングも並んでいた。ユーザーのフィードバック：「なぜか別々の3つのUIで実装されているのが違和感」「フィルタのUIなのかソートのUIなのかパッと見で理解できない」。

- **役割が同じ操作は、軸が違っても1つのUIに畳む**。増える方向（軸を足す）は「＋条件 → 軸を選ぶ → 値を複数選ぶ」の条件チップ方式で吸収し、軸ごとに専用のセレクトを生やさない。軸が10個に増えてもツールバーの構造は変わらない
- **絞り込みの軸定義と、束ね方（グルーピング）の軸定義は同じ1枚の表から作る**（`dashboard_board.py` の `AXES`）。別々に持つと「絞れる粒度と束ねる粒度が違う」というズレが後から必ず出る
- **役割の違う操作ブロックの先頭には役割アイコンを置く**（絞り込み＝漏斗 / 並べ替え＝ソート記号 / 束ね＝レイヤー）。ラベル文字を足すより幅を食わず、同じ見た目のセレクトが並ぶ問題が解ける。アイコンは `dashboard_icons.UI_PATHS` が単一情報源（§9）
- **アイコンとその操作は1かたまり（`.tb-grp`）にして一緒に折り返す**。バラで並べると幅が狭い時にアイコンだけが前の行の端に取り残され、何の記号か分からなくなる（400px幅の実機確認で発覚）
- 検索欄など幅可変の入力は、狭い画面で `width:100%` にしない。`.tb-grp` のフレックス子として `flex:1 1 120px` で伸ばす（100%だとアイコンを押し出して別行に落とす）
- 絞り込みの行が複数あるときは、**漏斗アイコンは先頭行に1つだけ**置き、続きの行は `padding-left:21px`（アイコン14px＋gap7px）で字下げして同じ束に属することを示す。行ごとに同じアイコンを繰り返さない

**適用範囲（2026-08-08 時点）**: `.tb-grp` / `.tb-ico` / `.tb-sep` は `dashboard_ui.RESPONSIVE_CSS`（全ページ注入）が単一の正で、タスクボード・図鑑・習慣・進捗・称号が使用中。静的ページ（`*/web/index.html`）は Python を呼べないので、HTMLに `<!--SHUKI_ICO:filter-->`（`<!--SHUKI_ICO:sort:16-->` のようにサイズ指定も可）と書けば `inject_shell()` が `dashboard_icons` のSVGへ差し替える。**静的ページのHTMLにSVGパスを直書きしない**（§9の単一情報源が崩れる）。

> 条件チップ（＋条件 → 軸 → 複数値）の共有アセット化は 2026-08-08 時点で**未実施**。タスクボードのみが持つ。図鑑・習慣のボタン列は値が3〜5個で常時見えている形のため、チップに置き換えると押す手数がむしろ増える（ユーザーと合意して見送り）。軸が増えて畳む必要が出た時に `/assets/toolbar.js` として切り出す。

## 2.5 全ページ共通の骨格は単一情報源から生成する（2026-08-03 追加）

タイトル・ナビ・戻る導線は、ページごとに個別実装しない。SHUKIは10ページ以上あり、各ページが
独自に「🏠戻るボタン＋タイトル＋nav」を書くと、padding・gap・要素の順序がページごとに微妙に
ズレていく（実例：ヘッダーの要素順序が「タイトル→ナビ」のページと「ナビ→タイトル」のページが
混在し、画面遷移のたびにメニューの上下位置が入れ替わって見える不具合が起きていた）。

- 共通の骨格（ヘッダー・ナビ・下部タブバー）は `dashboard_ui.page_header()` 等の**1つの関数**が生成し、各ページはそれを呼ぶだけにする。個別ページの `<style>` に `header`/`.hbtn` 等を重複定義しない
- **ヘッダーは構造で固定し、CSSの折り返しに配置を委ねない**。「タイトル行」と「ナビ行」を別のブロック要素として分離し、ナビは `flex-wrap` で折り返させず横スクロールにする。1行に詰め込んで `flex-wrap:wrap` に頼ると、ボタン数やタイトルの長さでページごとに折り返しタイミングが変わり、「ページによって配置が違う」不安定さの直接原因になる
- 現在地を示すナビ項目は**常に同じ位置に表示**し、リンクでなく非活性表示にする（項目を配列から除外する方式は、除外分だけ幅が変わり配置が動くため避ける）
- 新しいページ・新しい導線（例：設定へのリンク）を追加するときは、まず「全ページに共通で要るか」を自問する。個別ページにだけ追加すると、次に同じ機能が要る場面で「なぜこのページにだけ無いのか」という不整合を再発させる

### 2.5.1 ヘッダー仕様（2026-08-06 確定）

「共通ヘッダー」と「世界観バンド」を分ける。前者は全ページ完全に同一、後者はページ固有。

| 層 | 中身 | 実装 | 揺らしてよいか |
|---|---|---|---|
| **共通ヘッダー** | SHUKIロゴ＋ページ名（左寄せ・1.15rem・sans）／ナビ行／設定導線 | `dashboard_ui.page_header()` のみ | ❌ 一切不可 |
| **世界観バンド** | サブ説明文・スコアカード・ヘルプボタン・タブ等 | 各ページの本文冒頭（`<div class="...-head">`） | ✅ ページの性格に応じて自由 |

- **静的ページ（習慣/図鑑/称号/家計）も共通ヘッダーを使う**。`index.html` の先頭に `<!--SHUKI_PAGE_HEADER-->` を置き、`inject_shell()` が `page_header()` を埋める。装飾ヘッダーに `<h1>` を持たせない（共通ヘッダーの h1 と二重になる）
- **共通ヘッダーはスクロールに追従する**（`position:sticky; top:0`）。ページを下までスクロールしてもナビが常に届く＝「戻るために一番上まで戻る」操作を消す
- 背景は `color-mix` の半透明＋`backdrop-filter:blur()`。図鑑・称号の背景グラデーションを不透明色で塗り潰さないため
- body に padding を持つページは `--page-pad-x` / `--page-pad-y` を宣言する。ヘッダーはこの値だけ負マージンで食い、画面端まで背景を伸ばす（サイドに本文が透けて流れる隙間を作らない）

### 2.5.2 近いページを束ねるならページの中でなくナビの中で（2026-08-21 確定）

「関連する3ページを1つにまとめたい」ときの手段は2つある。**タブで1ページに集約する**（内側で束ねる）か、
**ナビのメニューにまとめる**（外側で束ねる）か。SHUKIは後者を既定にする。

前者を実際にやって失敗した記録（📡管制室・生活/家計/トレード。2026-08-20導入→08-21撤回）：

- 既存ページを再利用するには iframe しかなく、**高さを親が同期し続ける**必要が出た（測る前に一度つぶす→再入ガード→ズレたら4回まで測り直し。それでも実測51px/71pxのズレと戦っていた）
- 幅の上限が二重にかかり、**実機390pxで中身が304pxに縮んだ**（19%減）。埋め込み時だけ外枠の余白を外す例外CSSが必要になった
- 埋め込み側の共通ヘッダー・下部タブバー・対話ドックを打ち消すCSSが6件。**共通の骨格（§2.5）を局所的に否定する**コードが増えた
- タブ行の吸着位置をJSでヘッダー実測して流し込む必要があった

つまり「1ページに見せる」ためのコストは全部レイアウトが払っていた。ナビ側で束ねれば、各ページは
**単独表示のまま1行も変えなくてよい**。

- グループは `dashboard_ui.NAV_PAGES` の `children` で宣言する（親はリンクを持たず、押すとポップオーバーが開く3択）
- グループ内のページを開いている間は**親をカレント表示にする**（現在地がナビから消えない・§2.5 の原則の継承）
- ポップオーバーは **body直下へ移して `position:fixed`** で開く。ヘッダーのナビ行は横スクロール（`overflow-x:auto`）なので、その中に `absolute` で置くとクリップされて一切見えない（2026-08-21 実測）
- モバイルは下部タブバーの**真上に全幅シート**で開く。狭いタブ幅に小さなメニューを出すと押した指自身で選択肢が隠れる

## 3. アフォーダンスとシグニファイア（SHUKI固有・最重要）

SHUKIサーバーは vault 本体の `.md` を**絶対に書かない**という不変条件がある。ボタンを押しても `POST /queue` → `99_System/ui-queue/` に積まれるだけで、実際の反映は次便の orchestrator 便まで起きない。これは普通のUIには無い性質で、黙っていると「押したのに変わらない＝壊れている」と誤認される。

**規約**：
- 非同期反映のボタンは押下直後に **楽観的更新**（行を薄グレー等に変える）＋「⏳ 次便で反映」バッジを必ず出す
- 同期反映（`/trading/params` 等・即座に効くもの）と非同期反映は**視覚的に区別**する（アイコンか色で）
- ボタンは「押せる／無効／実行中／反映待ち」の4状態を必ず持つ。無効なのに押せる見た目、実行中なのに変化がない、は禁止

## 4. フィードバックと時間

Nielsenの閾値をそのまま採用：0.1秒＝即時に感じる境界、1秒＝思考が途切れない境界、10秒＝離脱が始まる境界。

- 10秒を超える処理（インデックス初回構築 約9.5秒等）は**ブロックしない**。進捗を返す（`{"building":true,"progress":0.4}` 形式）
- `claude -p` ジョブは既存の `_stream_apply()` が逐次表示を持っている。新しい非同期処理もこの流儀に揃える

## 5. モーション

目的は「変化の説明」に限定する（カウントアップ・バーの伸長・NEW!バッジの点灯）。物語演出（討伐・戦闘リザルト等）はモーションでは補わない。

> 「刺さったのは**触って・見て楽しいUI**であって物語文体ではない」（`memory/gamification-playbook.md`、2026-07-20 ユーザーのフィードバック）

`prefers-reduced-motion: reduce` を必ず尊重し、アニメーションを切れるようにする。

## 6. タッチと到達域

スマホ（Tailscale経由）が実運用に入っている。

- タップ標的は**44px以上**（`dashboard_ui.RESPONSIVE_CSS` の `.bn-item { min-height:44px }` が既存実装）
- 主要操作は画面下部（親指の到達域）に置く。下部固定タブバーはこの原則の実装

## 7. 一貫性と検証

- 数値表示は `gamification-playbook` の温度ルールを継承：**偽精度禁止**（「¥103,250」ではなく「¥10万規模（推定）」）、測れないものは「極小〜特大」の定性表現でよい、**メリット・デメリットは必ず両方**書く
- 変更後は**ヘッドレスChromeでスクショ→Read で目視検証**してから完了と言う（`AGENTS.md` §🛠 図・グラフの既存手順を画面UIにも適用）
- **モバイルの横はみ出しは目視だけでは気づけない。数字で測る**（2026-08-21 追加）。390px幅で `document.documentElement.scrollWidth` と `clientWidth` を比べ、差が出たら**必ず原因要素まで特定してから直す**（全要素の `getBoundingClientRect().right` を見て絞る）。実際に3ページで見つかった原因は全部CSSの書き方で、見た目の印象からは推測できなかった：
  - `grid-template-columns:1fr` … `1fr` は最小幅が min-content。中身の折り返せない要素までトラックが広がる。**`minmax(0,1fr)` と書く**（実測: ホームが741px＝右半分が画面外）
  - `repeat(auto-fit, minmax(420px,1fr))` … 画面が420pxより狭くてもトラックが縮まない。**`minmax(min(420px,100%),1fr)`**（実測: `/trading` 441px・`/finance`）
  - `display:flex` で `flex:0 0 <px>` のアイテムが並ぶ行 … 合計が親を超えても縮まない。**`flex-wrap:wrap` を付ける**（実測: `/trading` の戦略パラメータ行）
  - はみ出しは**ページ全体を画面幅より広げる**ため、`position:fixed; left:0; right:0` の下部タブバーまで一緒に広がって最後のタブが画面外に出る＝一見無関係な場所が壊れて見える
- 実物見本は `/styleguide`（`dashboard_views.py` 系・次フェーズで整備）に集約し、この文書を「読むだけの規約」で終わらせない

## 8. 実績・記録ダッシュボード編（草・推移・アチーブメント）

1〜7章は**操作する画面**（タスク・決裁）の作法。この章は**実績を見る画面**（`02_Home/` の草・推移・称号をサーバーへ移す系統）専用に追加した（2026-07-28）。

### 8.0 ゲージを作る前に「増えるのが良いのか、減るのが良いのか」を決める（2026-08-06 追加）

進捗ゲージ（バーが伸びる＝達成）は**多いほど良い量**専用の器。**少ないほど良い量**（支出・所要時間・エラー件数）に同じ器を使うと、バーが伸びるほど達成に見えて真逆の行動を促す。

- 実例: 変動費の「目標」ゲージを資産Lvゲージと同じ形で作ったところ、ユーザーから「変動費はむしろ減らしていくべきでは。**今は10万達成を目指しているみたい**」と指摘された。文言も「目標まで あと ¥17,265」＝「あと1.7万円使ってよい」と読める状態だった
- **減らす量では「目標」という語を使わない**。「上限」「越えてはいけない線」と書く。残余は「あと◯円」（使える額に見える）でなく「上限まで ◯円 残っている」
- **主役は水準でなく増減の向き**にする。「前月比 ▼¥101,034 減った」の方が、上限に対する達成率より行動に効く。減=`--ok`系／増=`--danger`系で向きを色でも示す

### 8.1 記録UIの目的は「褒める」ことではなく「続きを促す」こと

GitHubの草が効くのは見た目が良いからではない。**仕組みとして**分解すると4つ：

| 仕組み | なぜ効くか | SHUKI での実装条件 |
|---|---|---|
| 粒度の固定（1日＝1マス） | 達成の単位が迷いなく決まる | 集計単位は必ず「日」。週平均・月合計に丸めない |
| 連続性の可視化 | 途切れが視覚的に痛い＝続ける動機 | ストリーク（現在／最長）を数値で併記する |
| 過去が消えない | 努力が蓄積として残る | 過去日は再計算で色が変わらないこと（`date` 基準。`mtime` 基準は過去が動くので不可） |
| 1画面に全期間が入る | 進歩を一望できる | 1年分がスクロールなしで収まること |

- **実績表示は過去の自慢ではなく、次の1手のトリガー**として置く。画面を見て「で、今日どうするか」が出てこないなら、その指標は載せる価値がない
- 検証：その画面を開いて**今日の自分の状態**（続いている／途切れた）が1秒で分かるか

### 8.2 0を責めない

空白のマスに「サボった」「未達」の意味を与えない。**事実（0件）だけを出す**。

> 反省とは自分を責める行為ではなく、次に向けて改善・学習する行為（`memory/user-reflection-is-learning`、2026-07-20 ユーザーの言語化）

- 赤・警告色を「記録がない日」に使わない（`--danger` は状態色であって不在の色ではない）
- 不在は**淡いサーフェス寄りの色**で沈める。責めるのでなく、埋めたくなる余白として出す
- 検証：0件の日に否定的な語（未達・サボり・失敗・×）が出ていないこと

### 8.3 グラフの作法は dataviz skill が唯一の正

配色・フォーム選択・6チェックは **dataviz skill**（`AGENTS.md` §🛠 で作成前必読）に委譲する。ここには**重複させず**、vault 固有の追加制約だけを書く：

- **Area 10色を「面」に使わない**（1章の識別トークン規則の具体化）。Area別のヒートマップ・塗りつぶし面積グラフは**作らない**。Areaを見せたいときは帯・凡例ドット・縁取りに留める
- 量（magnitude）は**1色の濃淡**（sequential）。同一画面に量のグラフが2つ並ぶ場合のみ2色目を使う
- 「Areaごとに色を変えたい」と思ったら、それは量ではなく**識別**の要求。categorical スロット順を使い、Area 10色は流用しない（意味が衝突する）
- 検証：`validate_palette.js` を通す。**濃淡ランプは `--ordinal`** で検証する（categorical 用の検証にかけると設計上必ずFAILするので、それを「不合格」と誤読しない）

### 8.4 「並べない」の記録版 — 1画面1グリッド

大原則「並べない」は記録画面でも同じ。**同じ形のグリッドを4枚縦に並べない**（vault版のアクティビティカレンダーは指標ごとに4枚積んでおり、これは4つの問いを同時に投げて1つも答えていない状態）。

- グリッドは**1枚**。指標は切替（タブ／セグメント）で入れ替える
- 内訳は**ツールチップと表**に逃がす（2章の逓減開示）
- 検証：スクロールせずに「今日の状態」に到達できること

### 8.5 時間軸は3つの型しか作らない

記録の画面を増やすときは、必ず次のどれかに翻訳してから作る。当てはまらないものは**作らない**。

| 型 | 問い | 形 |
|---|---|---|
| 続いているか | 途切れていないか | 草（日次ヒートマップ）＋ストリーク |
| 伸びているか | 積み上がっているか | 累積・推移の折れ線 |
| 偏っていないか | 特定Areaに寄っていないか | 構成比（横棒・レーダー） |

### 8.6 データ品質を黙って隠さない

実績は実測値なので推定は不要だが、**元データが不確かな場合はその旨を出す**。

- 実例：完了タスクの `end_actual` 保有率は約17%しかなく、`/progress` は `end_actual→date→created` のフォールバックと `is_estimated` フラグで確定／推定を区別している（2026-07-28 時点）。同じ扱いを実績系にも適用する
- 「それらしい数字」を埋めて滑らかに見せない。欠損は欠損として見せる（`/finance` の「未確定」表示と同じ流儀）

### 8.7 語彙は②実務ダッシュボード系統

`memory/gamification-playbook` の3系統でいうと、実績・記録は **②実務ダッシュボード**（今の状態を把握する）。

- 使ってよい：ストリーク・連続・Lv・EXP・ランク（ゲージ語彙）
- 使わない：討伐・冒険・戦闘リザルト等の物語文体
- やるべきは**演出**：ロード時に草がフェードインする、ストリーク数がカウントアップする、といった「変化の説明」（5章）
- 例外：`/achievements`（称号バッジ図鑑）だけは①収集品系統なので画像・レアリティ演出が自由

### 8.8 サーバーだからできること（移植で終わらせない）

Obsidian版をそのまま移すだけなら移す意味がない。サーバーが**原理的に**持つ優位は4つで、実績画面を作るときは最低1つを使う：

| 優位 | Obsidian では | SHUKI では |
|---|---|---|
| 状態の保存 | 開くたび再計算＝「今」しか出せない | スナップショットを貯めて「先月の自分」と比較できる |
| 既読ポインタ | なし | 「前回見た時からの差分」を出せる（index の mtime） |
| 外部データとの結合 | vault 内で完結 | git commit・家計CSV・カレンダーを同じ時間軸に重ねられる |
| 能動性 | 見に行かないと分からない | 通知・朝ラジオで向こうから来る |

ただし**vault 本体の `.md` を書かない不変条件は記録系でも同じ**（3章）。集計結果を vault に書き戻さない。

## 9. アイコンの様式統一（2026-08-03 追加）

「アイコンがかっこよく見えない」の正体は分かりやすさの問題ではなく**様式が統一されていないこと**（絵文字は分かりやすいが、OS・フォントごとに描画が変わり配色トークンにも乗らないためチープに見える。配色刷新プロジェクトでユーザーと実物比較して判明）。

- **画面の意味的アイコン（ナビ・称号ランク・Area・期限状態等）は絵文字でなく線アイコンSVGに統一する**。絵文字は装飾用途でも新規に増やさない
- 1画面内でアイコンの**ストローク幅・角の丸み・線か塗りか**を統一する。「あるボタンは太い丸角、別のボタンは細い直角」のような混在が統一感を壊す。様式は事前に1つ選んでから全アイコンをそれに合わせる（例：ストローク幅1.5・角丸小・アウトラインのみ）
- **同じ意味を持つアイコンは単一情報源（1箇所）で定義し、複数ファイルに重複定義しない**。SHUKIでは称号ランク（Bronze/Silver/Gold等）の表現が `achievements.py` 2箇所・`dashboard_ui.py`・`achievements/web/app.js` の計4箇所にバラバラに定義されており、様式を変えても一部だけ古いまま残る不具合の温床になっていた（2026-08-03発見）。新設・変更時は真っ先に「他に同じ意味を描いている場所はないか」を検索する

## 10. マイクロコピー・文言のトーン（2026-08-04 追加）

「今日のログまだ書いてないよ」のようなくだけた語尾と、「✓ 変更を予約しました」のような事務的な語尾が画面ごとに混在し、統一感を欠いていた（2026-08-03〜04 UI刷新プロジェクトでユーザーと洗い出して判明）。**目的は人格を前面に出すことではなく統一感**。ただし奥にうっすら一貫した「声」を感じさせることで、無機質な操作画面以上の興味を持たせる効果を狙う（デザイン言語.mdの文体ルールはユーザー自身の発信が対象、こちらはSHUKIがユーザーに語りかける文言が対象で主体が異なる）。

### 10.1 人格の輪郭：寡黙な記録係

- 感情表現は控えめ。装飾語・絵文字・感嘆符を使わない
- 褒めすぎない、責めない（8.2「0を責めない」の精神をエラー・空状態にも一貫させる）
- エラーでも突き放さず、事実を淡々と伝えたうえで次の一歩を添える
- **「見当たりません」「〜のはずが」等、探索して不在を確認したニュアンスの語は使わない**。あるべきものが欠けている、催促されている、という含意を持たせず、ただの事実描写に留める（例：「本日はまだログが記録されていません」であって「本日のログが見当たりません」ではない）
- **「〜しよう」のような勧誘語尾も使わない**（2026-08-04・実装時に「不自然」と指摘され確定）。行動を促したい場面（フォーカス帯タイトル等）は勧誘せず、「まず1つから」「次の1つへ」のように**体言止め・助詞止めで方向だけ指し示す**。呼びかけの機能（背中を押す）は残しつつ、語尾に人格を乗せない

### 10.2 一人称の使用範囲

- **語りかける場面（フォーカス帯アラート等、能動的にAIから話しかける文言）だけ**で、控えめに人格を覗かせてよい
- **機械的通知（トースト・空状態・ボタンラベル）は無人称のまま**。全画面に人格を敷き詰めない（敷き詰めるとキャラクターが前面に出すぎて「統一感」という主目的からズレる）

### 10.3 実例（2026-08-04 合意）

| 場面 | 文言 |
|---|---|
| フォーカス帯タイトル（期限あり） | 期限切れ N件 — まず1つから |
| フォーカス帯タイトル（期限なし） | 今日は締切なし — 次の1つへ |
| フォーカス帯アラート | 本日はまだログが記録されていません |
| トースト成功 | 変更を予約しました。次便で反映します |
| トーストエラー | 予約できませんでした（詳細エラー） |
| 空状態（実行履歴） | 実行履歴は、まだありません |
| 空状態（クエスト効果） | 効果は未生成です（次回バッチで付与） |

エラートーストは「予約」「レビュー済みに」「メモを予約」など**操作の動詞を都度当てはめ**、末尾に詳細エラー（`e`）を括弧書きで添える。定型句1つで済ませない。

### 10.4 適用範囲

対象は実務的な文言（トースト・空状態・フォーカス帯アラート・エラーメッセージ）。**称号・ゲーミフィケーション語彙（ストリーク・Lv・EXP・ランク名等）は対象外**（8.7で既に「実務ダッシュボード」語彙として規定済み・物語文体は使わない）。
