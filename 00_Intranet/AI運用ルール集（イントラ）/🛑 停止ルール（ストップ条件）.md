# 🛑 停止ルール（ストップ条件）

> [!warning] 🛑
>
> **無駄なループはコスト（時間・トークン課金）を生む。** 解決できない状況で試行錯誤を続けるより、**早く止まって人間に渡す**方が安く・速い。
>
> これは [[🛠 Technical Setup]] §モデル戦略 とは別レイヤーのルール。モデルの選び方ではなく「**いつ手を止めるか**」を定める。Claude Code 本体・全エージェント・スキルに適用。

## S.1 停止条件（該当したら作業を継続しない）

以下のいずれかに該当したら、リトライや回避策の試行錯誤を**続けず**に停止し、§S.2 のフォーマットで人間（ユーザー）に渡す。

1. **認証エラー** — ログイン・トークン・APIキーが無効／期限切れ
2. **権限エラー** — 書き込み拒否・read-only・アクセス権不足でファイル操作やコマンドが通らない
3. **致命的エラー全般** — レート制限／API制限／セッション上限、容量・トークン超過、I/Oエラーなど、リトライで状況が変わらない種類のエラー
4. **外部サービスへの接続失敗** — ネットワーク不通・タイムアウト・サービス側ダウン
5. **同じエラーが2回以上連続** — 1回目で原因が分からないなら、同じやり方の繰り返しは無駄。やり方を変えられないなら止まる
6. **入力ファイルが大きすぎて全体把握に時間がかかる** — 全体を読み切らないと判断できないのに、サイズが現実的でない
7. **解決に必要な情報が不足** — 前提・指示・データが足りず、推測で埋めると捏造になる場合（→ 推測で進めない。[[✅ タスク管理ルール]] の completion_criteria が書けないのと同じ）
8. **泥沼パターンの自覚（2026-07-04 導入・[[✂️ 作業規律]]）** — 作業中に以下の4パターンに入っていると気づいたら、強行せず停止してユーザーに確認する。エラーではないため §S.2 の「エラー本文」は「何がどう膨らんでいるか」に読み替える：
   - **キッチンシンク**: 小さな修正の依頼なのに、広範囲の改修・再編を始めている
   - **暴走するリファクタリング**: 1ファイルの整理のつもりが、無関係なファイルへの分割・改名・移動が連鎖している
   - **楽観的パス**: 正常系だけ考え、エラー処理・接続切れ・不正入力・既存データの壊れを無視している
   - **誤った抽象化**: 同じ情報・ロジックのコピペ量産、または逆に不要な共通化・概念ノードの乱造をしている

> [!note] 判断のコツ
>
> 「**あと1回試せば直るか？**」が読めないなら、それは止まるサイン。直る見込みが説明できる時だけ続行する。

## S.2 停止時に出力するもの（これだけ）

停止したら、長い経過説明は書かず**以下の5項目だけ**を出力する：

```
🛑 停止しました

1. どこで止まったか：<ファイル名・コマンド・ステップ>
2. エラー本文：<エラーメッセージをそのまま貼る。要約しない>
3. 推定原因：<1〜2行。分からなければ「不明」と書く>
4. 人間が確認すべきこと：<ユーザーが判断・操作すべき具体アクション>
5. 再開用の最小プロンプト：<このまま Claude Code に渡せば作業を再開できる最小指示>
```

- **エラー本文は改変しない** — 要約・意訳すると原因究明できない。原文を貼る（[[🔄 QAサイクル]] §10.3 アンチスロップ「未記入を明示／値を創作しない」と同じ精神）
- **推定原因が分からなければ「不明」** — もっともらしい原因を創作しない
- **5の最小プロンプト** — ユーザーが問題を解消した後、文脈を再説明せずに貼るだけで続きを再開できる粒度にする

## S.3 ループを生まないための事前ルール

止まる前に、そもそも無駄ループに入らないための原則：

- **同じ操作を3回以上繰り返さない** — 2回失敗したらアプローチを変える。変えられないなら §S.1-5 で停止
- **リトライは数えながら** — 「失敗 → 同じ手で再試行」を無限に続けない。Task Scheduler 側の自動リトライ（失敗時30分後・最大3回）と二重に回さない
- **大きい入力は先に範囲を絞る** — 全件読みが必要か見極め、不要なら対象を限定してから着手（→ 全件読みが必須な作業は `/message-review` スキル §入力 のように明示されている場合のみ）
- **不明点は推測で埋めず先に聞く** — 解決に必要な情報が欠けているなら、試行錯誤より先にユーザーへ確認

## S.4 解消後の教訓記録（失敗からの学習・2026-07-03 導入）

停止・失敗が**解消したら**（ユーザーの対応後に再開した時、または自力でアプローチを変えて成功した時）、同じ失敗を繰り返さないために [[📚 教訓集]] に1エントリ残す。次のセッション・別のエージェントがこの学びを引き継ぐ。

- **書くのは事実だけ**：「起きたこと（エラー原文の要点）」「効いた対策（実際にやって直った操作）」「適用範囲」の3行。**推測の原因論・一般論の再発防止策は書かない**（LLMの自己分析には幻覚リスクがある — Local AI QA 廃止と同根の教訓）
- 🔴ゾーン絡みの教訓はユーザーの確認後に記録する。それ以外は AI 判断で書いてよい（ただしエラー原文を改変しない）
- **同種の教訓が3件たまったら**、ルールファイル本体への昇格をユーザーに提案する（概念ノードの「3件ルール」と同じ閾値。`/ops-review` の材料になる）
